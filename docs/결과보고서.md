## 2. 실습 목표

일반 LLM은 우리 회사의 반품·배송·멤버십 규정을 정확히 모를 수 있다. 이번 실습의 목표는 사내 문서를 검색해 근거로 제공하고 AI가 그 근거 안에서만 답하도록 만드는 것이었다.

1. Markdown 문서 3종을 청크로 나눈다.
2. 청크를 임베딩해 `VectorStore`에 저장한다.
3. 질문과 유사한 청크를 검색한다.
4. 검색한 문서만 AI의 근거로 사용한다.
5. 문서에 없는 질문은 추측하지 않고 거절한다.
6. 골든 세트와 A~F 실험으로 RAG 품질을 측정한다.

## 3. 아키텍처와 기술 스택

```text
클라이언트
  → Lab2Controller
  → Lab2IngestService / Lab2QnaService
  → TextReader → TextSplitter → EmbeddingModel → SimpleVectorStore
                                                    ↓ 유사도 검색
                                                ChatClient
                                                    ↓
                                               AnswerDto
```

Controller가 `ChatClient`나 `VectorStore`를 직접 호출하지 않고 Service에 위임하도록 계층을 분리했다. HTTP 처리, 문서 검색, AI 호출의 책임을 분리해 테스트와 유지보수가 쉽다.

- Java 21, Spring Boot 4.1.0, Spring AI 2.0.0
- Chat Model: `gpt-4o-mini`
- Embedding Model: `text-embedding-3-small`
- Vector Store: `SimpleVectorStore`
- Swagger UI, JUnit 5, AssertJ

## 4. Step 1 — 문서 인제스트

`Lab2IngestService`에 다음 파이프라인을 구현했다.

```text
Markdown 문서 읽기
  → 청크 분할
  → source/version 메타데이터 추가
  → 기존 문서 청크 삭제
  → 임베딩 및 VectorStore 저장
```

적재 대상은 `return-policy.md`, `shipping-policy.md`, `membership.md` 3종이다.

### 핵심 구현

- 현재 자료는 PDF·DOCX가 아니라 Markdown이므로 불필요한 `TikaDocumentReader` 대신 `TextReader`를 사용했다.
- 한글 깨짐을 막기 위해 UTF-8을 명시했다.
- 검색·출처 표시·재색인에 쓰는 `source`, `version`을 인제스트 시점에 추가했다.
- 같은 문서를 두 번 적재해도 청크가 누적되지 않도록 `source` 필터로 기존 데이터를 지운 후 저장했다.

```java
var sourceFilter = new FilterExpressionBuilder()
        .eq("source", source)
        .build();
vectorStore.delete(sourceFilter);
vectorStore.add(chunks);
```

## 5. Step 2 — 유사도 검색

`Lab2QnaService.retrieve()`는 질문을 임베딩한 뒤 가장 유사한 청크를 찾는다.

```java
SearchRequest request = SearchRequest.builder()
        .query(question)
        .topK(topK)
        .similarityThreshold(similarityThreshold)
        .build();
```

검색 API는 `source`, `score`, 최대 120자의 `snippet`을 반환한다. 점수와 원문을 노출한 이유는 AI 답변 이전에 **올바른 근거를 찾았는지** 직접 확인하기 위해서다.

초기에 결과가 `[]`로 나온 원인은 인제스트 전의 `SimpleVectorStore`가 비어 있었기 때문이었다. `/lab2/ingest`를 먼저 호출하자 결과가 나왔다. `SimpleVectorStore`는 인메모리 저장소이므로 서버 재시작 후에도 다시 인제스트해야 한다.

## 6. Step 3 — RAG 답변 생성

```text
질문 검증 → 유사도 검색 → 근거 포맷팅
          → ChatClient 호출 → AnswerDto 반환
```

### 문서에 없는 질문 거절

검색 근거가 없으면 AI를 호출하지 않고 즉시 다음을 반환한다.

```json
{
  "answer": "확인되지 않습니다.",
  "sources": [],
  "grounded": false
}
```

코드 수준의 거절은 환각을 막고 불필요한 모델 호출 비용도 줄인다.

### 안전한 프롬프트와 구조화 출력

사용자 입력을 문자열에 직접 더하지 않고 `{question}`, `{context}` placeholder와 `.param()`으로 바인딩했다. 응답은 문자열 파싱 대신 `responseEntity(AnswerDto.class)`로 받아 답변·출처·근거 여부를 각각 검증할 수 있게 했다.

`finishReason=length`이면 잘린 JSON을 정상 결과로 오판할 수 있으므로 예외를 발생시키도록 구현했다. 답변의 재현성을 높이기 위해 temperature는 0.0, max tokens는 300으로 고정했다.

## 7. Step 4 — 골든 세트 평가

`Lab2GoldenSetTest`에서 `golden.json`의 10개 질문을 실제 RAG 서비스에 입력하고 다음을 검사하도록 구현했다.

1. `must`의 필수 단어가 답변에 모두 있는가?
2. 예상 `src`가 출처에 포함되었는가?
3. 문서에 답이 있으면 `grounded=true`인가?
4. 문서에 답이 없으면 `grounded=false`인가?

테스트 프로세스의 VectorStore는 서버와 다르므로 `@BeforeEach`에서 문서 3종을 자동 인제스트했다. 평가 통과 기준은 **8/10 이상**으로 고정했다.

```bash
export OPENAI_API_KEY="발급받은 키"
./gradlew test -Peval --rerun-tasks --console=plain
```

> 현재 작업 셸에는 `OPENAI_API_KEY`가 전달되지 않아 실제 점수를 임의로 작성하지 않았다. 키가 등록된 터미널에서 위 명령을 실행하고 `통과 N/10`을 최종 점수로 기록한다.

## 8. Step 5 — A~F 실험

| 조합 | 청크 | 겹침 | top-k | threshold | 목적 |
| --- | ---: | ---: | ---: | ---: | --- |
| A | 400 | 0% | 4 | 0.0 | 기준선 |
| B | 200 | 0% | 4 | 0.0 | 작은 청크의 정확도·맥락 손실 |
| C | 800 | 0% | 4 | 0.0 | 큰 청크의 맥락·잡음 |
| D | 400 | 0% | 8 | 0.0 | 검색 범위 확대 |
| E | 400 | 0% | 4 | 0.7 | 엄격한 검색과 거절 증가 |
| F | 400 | 20% | 4 | 0.0 | 청크 경계 손실 완화 |

Spring AI 2.0 `TokenTextSplitter.Builder`에는 overlap 설정 메서드가 없어 F 실험용 `OverlapTokenTextSplitter`를 추가했다. 기본 겹침은 0%라 A~E의 동작에는 영향이 없다.

### 실험 결과 해석 기준

A~F 실험의 핵심은 단순히 가장 높은 점수를 찾는 것이 아니라, **어떤 설정이 검색 품질을 바꾸었는지 원인을 설명하는 것**이다. 실측 점수가 아직 없으므로 아래 내용은 결과를 판독하기 위한 기준으로 사용한다.

#### A — 기준선

A는 다른 조건을 판단하는 기준이다. B~F의 점수만 보지 말고 A에서 실패한 문항의 검색 청크, 출처, 답변을 함께 남겨야 설정 변경의 효과를 비교할 수 있다.

#### B — 작은 청크

B의 점수가 A보다 오르면 현재 문서의 규정이 짧은 사실 단위로 잘 나뉘어 검색 정확도가 높아졌다고 볼 수 있다. 반대로 점수가 내리면 질문에 필요한 조건과 결론이 서로 다른 청크로 잘려 맥락이 부족해졌을 가능성이 크다.

#### C — 큰 청크

C가 개선되면 한 번에 넓은 규정 맥락을 제공한 것이 도움이 된 것이다. C가 나빠지면 관련 없는 내용까지 하나의 벡터에 섞여 질문과 핵심 규정 사이의 유사도가 흐려졌거나, LLM에 넘어간 잡음이 늘었다고 해석할 수 있다.

#### D — top-k 확대

D의 점수가 오르면 필요한 근거가 기존 4개 밖에 있었다는 뜻이다. 점수가 같다면 추가 4개의 근거가 답변에 도움이 되지 않으면서 토큰 사용량과 지연 시간만 늘릴 수 있다. 점수가 떨어진다면 관련성이 낮은 청크가 프롬프트에 섞여 모델이 올바른 근거에 집중하지 못한 것이다.

#### E — 유사도 임계값 상향

E는 검색 정확도와 거절율의 균형을 보는 조건이다. `우주 배송`과 같은 문서 밖 질문의 거절은 늘을 수 있지만, 임계값이 너무 높으면 정상 질문의 근거도 제거해 오탐 거절할 수 있다. 따라서 전체 점수뿐 아니라 `src=null`인 문항과 정상 문항의 통과 여부를 따로 비교해야 한다.

#### F — 20% overlap

F가 A보다 좋아지면 정답에 필요한 문장이 청크 경계에서 잘리던 문제가 완화된 것이다. 차이가 없다면 현재 문서가 짧고 규정 단위가 명확해 overlap의 이점이 작았다고 볼 수 있다. 낮아진다면 중복 근거가 상위 결과를 차지해 다른 필요한 청크를 밀어냈는지 확인해야 한다.

### 최종 설정 선택 기준

최종 설정은 통과 문항 수만으로 결정하지 않는다. 동점이라면 더 작은 top-k, 더 적은 중복 청크, 더 짧은 프롬프트를 만드는 조건을 우선한다. 즉 **골든 세트 정확도, 잘못된 거절, 출처 정확성, 토큰 비용, 응답 지연**을 함께 보고 균형이 가장 좋은 조건을 선택해야 한다.

```bash
export OPENAI_API_KEY="발급받은 키"
./scripts/run-step5-experiments.sh
```

결과는 `build/step5-experiments/summary.md`, `summary.html`, `A.log`~`F.log`에 저장된다. 실험 때 Gradle이 이전 결과를 `UP-TO-DATE`로 재사용하지 않도록 스크립트에 `--rerun-tasks`를 적용했다.

```bash
open build/step5-experiments/summary.html
```

## 11. 개인 회고

이번 실습을 통해 RAG는 단순히 LLM에 문서를 넘겨주는 기능이 아니라, **문서 읽기 → 청크 분할 → 임베딩 → 검색 → 근거 조립 → 답변 생성 → 평가**로 이어지는 전체 파이프라인이라는 것을 이해했다.

구현 과정에서 가장 먼저 마주친 문제는 `TikaDocumentReader`로 인한 `bootRun` 실패였다. 처음에는 문서를 읽는데 보통 사용하는 도구라고 생각했지만, 현재 자료는 PDF나 DOCX가 아니라 Markdown이었다. 문서 형식에 맞는 `TextReader`로 바꾸면서 기능이 많은 도구보다 **현재 데이터에 맞는 도구를 선택하는 것**이 중요하다는 점을 배웠다.

그다음 `/retrieve`가 `[]`를 반환했을 때는 처음에 검색 로직을 의심했지만, 실제 원인은 VectorStore에 문서를 인제스트하지 않은 것이었다. `/lab2/ingest`를 먼저 호출하자 정상적으로 검색되었고, 골든 세트 테스트에는 `@BeforeEach`로 자동 인제스트를 넣어 외부 실행 순서에 의존하지 않게 했다. 이 과정을 통해 RAG를 디버깅할 때는 AI 답변보다 **문서가 실제로 저장되었는지, 그리고 올바른 근거가 검색되었는지**를 먼저 확인해야 한다는 것을 알게 되었다.

테스트가 `UP-TO-DATE`로만 표시된 것도 초기에는 오류처럼 보였다. 하지만 이것은 Gradle이 이전 결과를 재사용한 최적화 동작이었다. 일반 테스트에서는 문제가 없지만, A~F처럼 매번 새로운 모델 호출 결과를 측정해야 하는 실험에서는 적합하지 않아 `--rerun-tasks`를 적용했다. 이를 통해 빌드 성공 여부뿐 아니라 **실험이 실제로 다시 수행되었는지**도 확인해야 한다는 것을 배웠다.

F 실험에서는 기본 `TokenTextSplitter.Builder`로 20% overlap을 직접 설정할 수 없어 `OverlapTokenTextSplitter`를 직접 추가했다. 분할 기능만 넣고 끝내지 않고 0%와 20% 분할, 메이타데이터 보존을 단위 테스트로 확인했다. 이 작업을 통해 청크 크기만이 아니라 **문장이 어디서 잘리는지와 인접 청크가 얼마나 겹치는지**도 검색 품질에 영향을 준다는 것을 이해했다.

가장 인상 깊었던 부분은 답변이 잘못되었을 때 무조건 프롬프트를 고치는 것이 아니라, `/retrieve`로 올바른 근거를 찾았는지 먼저 확인해야 한다는 점이었다. **근거를 찾지 못한 문제**와 **근거를 찾고도 잘못 답한 문제**는 수정할 위치가 다르다. 전자는 청킹·임베딩·top-k·threshold를, 후자는 프롬프트·근거 포맷·모델 출력을 중점적으로 봐야 한다.

또한 문서에 없는 내용의 환각을 막으려면 프롬프트만으로는 부족하며, 검색 결과가 없을 때 모델을 호출하지 않는 코드 수준의 방어가 필요하다는 것도 배웠다. 이 방식은 정확성을 높이는 동시에 불필요한 API 비용도 줄인다.

향후에는 A~F 실측 결과를 비교해 정확도와 비용의 균형이 가장 좋은 조건을 선택하고, `SimpleVectorStore`를 pgvector와 같은 영속성 있는 저장소로 전환해 서버 재시작 후에도 임베딩 데이터가 유지되도록 확장해 보고 싶다.
